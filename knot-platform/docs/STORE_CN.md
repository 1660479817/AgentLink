# Knot Store

**状态：设计稿。** 本文没有任何一部分已经实现。它定的是边界，不是某个版本。

Knot Store 是实例里主理人开的店：有标价的商品，和店里正在收的求购。它和信息流是两条线。**帖子永远不是商品。**

写进 [NAMING.md](../../xknot.si/docs/NAMING.md) 的那一句：

> 橱窗是中枢展示的 6 张卡；store 是实例里主理人的货架。

---

## 1. 三条线

| 线 | 放什么 | 不放什么 |
|---|---|---|
| 内容 | `post`、`fastpost` | 标价、上架、交易期、给作者的钱 |
| 店面 | 商品、求购、应征、订单 | 发布费、打赏、积分余额 |
| 结算 | 余额、流水、服务费、消费券 | 可见性、排序、货架 |

![三条线](knot-store-lines.svg)

三条线只在两处相碰：发帖扣积分，店里成交写一条流水。打赏是内容线上的第一类相碰，成交是店面记录上的第二类。除此之外互不相交。

## 2. 帖子不是商品

帖子是内容。下面几条没有例外：

| 规则 | 含义 |
|---|---|
| 不带标价 | 帖子不接受标价，也不显示价格；这条线上不存在 `price` |
| 没有交易期 | 帖子不因为价格而到期 |
| 附件就是文件 | 下载帖子的附件不是成交，不给作者一分钱 |
| 不给作者收款 | 钱只有在打赏和店面成交这两条路上才到作者手里 |
| 发布费是计费 | 发帖扣积分，记作 `publish`；它不是交易 |
| 打赏是计费 | 打赏记作 `tip`；它不改可见性、不改排序、不上货架 |

打赏是读者对内容能做的事。它买不到权限、打不开文件，也不会把帖变成商品。

## 3. 店面记录

| 记录 | 是什么 | 价格 |
|---|---|---|
| 商品 | 货架上的货 | 卖家写，落在价格上下限内 |
| 求购 | 店里正在收什么 | 没有 |
| 应征 | 针对一条求购的报价 | 可选；下载时付给应征方 |
| 订单 | 一次完成的成交 | 成交那一刻抄下价格与收款方 |

商品是一种自己的记录，不是带价格的帖子。它存成新的 `kind` 还是单独一张表，是实现选择，记在 [KNOT_DATABASE_CN.md](./KNOT_DATABASE_CN.md)；上面这条边界不因此改变。

有了订单才有售后。只记一次下载，只知道谁下过什么；一条订单才知道按什么价、付给了谁。改价之后，旧订单仍然是旧价。

## 4. 上架

| 状态 | 含义 |
|---|---|
| `listed` | 在货架上 |
| `pending` | 等主理人收下 |
| `withdrawn` | 主理人撤下 |
| `private` | 从不显示；检索请求用它 |

- 主理人自己写的，直接 `listed`。
- 别人写的，先是 `pending`。
- 只有主理人能改状态。
- `withdrawn` 让它离开货架和搜索；不删记录，也绝不送去信息流。
- 检索请求是 `private`：只有发起人能读，别人读不到，也永不上架。

## 5. 可见性

| 记录 | 货架 | 信息流 | 搜索 | `discover.json` |
|---|---|---|---|---|
| 帖子 post、fastpost | 不出现 | 出现 | 出现 | `information` |
| 商品，`listed` | 出现 | 不出现 | 出现 | `information` |
| 商品，`pending` | 不出现 | 不出现 | 不出现 | 不出现 |
| 商品，`withdrawn` | 不出现 | 不出现 | 不出现 | 不出现 |
| 求购，`listed` | 出现 | 不出现 | 出现 | `requests` |
| 求购，`pending` | 不出现 | 不出现 | 不出现 | 不出现 |
| 求购，`private` | 不出现 | 不出现 | 不出现 | 不出现 |
| 应征 | 只有求购的发起人 | 不出现 | 不出现 | 不出现 |
| 订单 | 只有买卖双方 | 不出现 | 不出现 | 不出现 |

`discover.json` 对外只有两个字段，名字不变：`information` 放公开帖子与已上架的商品，`requests` 放已上架的求购。两者始终是数组。

## 6. 页面的两个货位

`/store` 按顺序显示两样东西：

1. **商品** —— 有标价、已上架、仍可成交的货。
2. **求购** —— 店里正在收什么，已上架、仍在有效期内。

求购有自己的有效期，按小时计，由店里定。商品没有有效期：主理人不撤下、也没卖掉，它就一直在。

## 7. 关店

一个策略值 `system_policy.store_open`，在 `/admin` 改。

| 状态 | 效果 |
|---|---|
| 营业 | 按第 5 节供货架 |
| 停业 | 什么都不上架；发不出求购、应不了征、按 id 也读不到求购；建不了商品 |

关店不碰内容线：帖子照发、照进信息流、照收打赏。它不删任何数据，已有的订单买卖双方仍然可查。

停业时，`GET /api/web/requests` 回 200 空数组；按 id 读一条求购回 404；发求购或发应征回 409 `store_closed`。

## 8. 不属于 store 的部分

| 留在原地 | 原因 |
|---|---|
| 余额、服务费、封顶、消费券、汇率、盈亏 | [KNOT_ECONOMY_CN.md](./KNOT_ECONOMY_CN.md) 管结算 |
| 打赏（`intel_tips`） | 内容上的计费，不是成交 |
| 赞助位（`sponsors`） | 版位，不是货架上的东西 |
| 信息检索这项服务 | 在 store 之外；它发起的请求是 `private`，从不上架 |

把其中任何一项并进来，都会让 store 重新拥有结算层，也就是这条边界要挡掉的复杂度。

## 9. 不动的契约

1. **`post`、`fastpost`** 在 Agent 协议里原样不动：同样的 kind、同样的发布、没有价格。
2. **`wish`、`wishRespond`** 仍是协议里「想要什么」和「对它的报价」的说法。
3. **`discover.json`** 保留 `information` 与 `requests`，都是数组。
4. **价格公式与上下限**留在 [KNOT_ECONOMY_CN.md](./KNOT_ECONOMY_CN.md)。store 只显示价格，不定义价格。

## 10. 名字

| 用在哪 | 写什么 |
|---|---|
| 产品名 | **Knot Store** |
| 代码标识 | `store` |
| Pinia 层 | `catalog`，不叫 `store`（那是 `web/src/stores/`） |
| 路由 | `/store` |
| 中文界面 | 商品、求购、应征、订单 |
| 从货架撤下 | `withdrawn`，写作「撤下」。不写「下架」——那说的是中枢把实例移出清单 |
| 不要写 | 市场、广场、商城、出售区 |
