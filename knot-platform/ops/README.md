# Deployment and operations

This directory is the **instance side** of the deployment layer: every Knot site deployed with `knot-platform` (WebUI + Backend + OpenClaw suite) is published from here.

Officially two **public shapes** are supported, independent of "which machine it runs on":

| Public shape | Public address | Config |
| --- | --- | --- |
| **local only** | `http://127.0.0.1:<KNOT_PORT>/` | `KNOT_DOMAIN=` empty, `KNOT_ENTRY_ENABLED=0`, `KNOT_TUNNEL=0`, Backend bound to loopback only |
| **xknot.si sub-subdomain** (public) | `https://<label>.xknot.si/` | `KNOT_DOMAIN=<label>.xknot.si`, via back-origin tunnel (+ entry nginx) |

The instance host can be an always-on machine (`bot01`) or the dev environment itself. **"local" only means the whole system runs on one machine, not that it can't go public**: the dev machine can also take a subdomain and join the federation (`cpswang` is exactly this — Backend on the dev machine, the entry host origin-fetching to its tunnel). In both shapes, Backend, Postgres, and the upload directory are all on this one machine; the entry only adds a copy of the WebUI and the public snapshot.

Who pushes the entry to the entry host decides `KNOT_ENTRY_ENABLED`:

- `1`: this machine's `push-entry.sh` pushes the WebUI and nginx conf at deploy time (`bot01`'s `wang.xknot.si`).
- `0`: don't touch the entry host. Either local only, or the hub has already auto-wired the entry and written the conf; this machine only runs the tunnel and content (`cpswang`).

**Standalone-domain deployment and intranet-exposure deployment are both outside the official scope**, they count as user customization. `config.mjs check` only accepts xknot.si-issued sub-subdomains, not self-owned domains, a fixed public IP direct connection, or LAN addresses.

Deployment has three layers:

- **Instance host**: runs Knot Backend, PostgreSQL, WebUI. macOS uses LaunchAgent, Linux uses systemd. Can be an always-on machine or the dev machine itself.
- **Public entry (subdomain shape only)**: one Linux + nginx, holding only the WebUI and the public snapshot, `/api` tunneled back to the instance host; the Agent guide is published by the hub at `xknot.si/knot-help`, the entry has no `/help`.
- **Config**: one `sites/<site>/site.env`; when taking a subdomain, add `entry.<label>.xknot.si.env` (when pushing the entry yourself) or `tunnel.env` (written by the UI after the hub auto-wires it).

Deployment splits into three steps that don't mix:

1. **Build** (dev machine): `ops/scripts/build.sh` produces `knot-<version>-<commit>-<platform>.tar.gz`;
2. **Install** (instance host): `deploy-site.sh` untars, migrates, switches `current`, restarts, probes — no `npm ci`, no `vite build`;
3. **Push** (dev machine, one command): `push-deploy.sh` = build + transfer + remote install + acceptance.

The target machine needs no source, no git, no build tools; only Node.js 22+ and a database.

Subdomain application, roster registration, and acceptance requirements are in [`xknot.si/docs/JOIN.md`](../../xknot.si/docs/JOIN.md); the partner-side join flow is in [`xknot.si/docs/HANDOFF.md`](../../xknot.si/docs/HANDOFF.md).

> Deploy scripts no longer hardcode IPs, domains, directories, or ports. Code, deployment, and config are separated: scripts live in `ops/`, one directory per site `sites/<site>/`. Templates in [`sites/_template/site.env`](../sites/_template/site.env), real site directories stay out of the repo.

## 1. Configuration

One directory per site, at most four config files in it. **Deployment and federation are two independent lines**:

| File | Governs | Written by | Read at deploy? |
| --- | --- | --- | --- |
| `sites/<site>/site.env` | site topology: public address, port, database, entry host, tunnel | ops | read |
| `sites/<site>/profile.json` | self-description zone: name, default locale, one-line intro, long intro, logo, owner, contact, region, timezone, tags (ten flat fields) | owner, edited in `/admin` | not read; read at Backend startup |
| `sites/<site>/entry.<label>.xknot.si.env` | the xknot.si subdomain entry: domain, static root, conf, cert, serve mode | ops | read |
| `sites/<site>/platform.env` | instance-host runtime: SMTP, prices, storage, admin token, mode `600` | generated by `deploy-site.sh` | read |
| `sites/<site>/xknot.env` | XKnot join: instance id, hub origin, issue date, delegated-mailing credentials, mode `600` | issued by the hub, written by `join-xknot.sh` | not read; only handed to the Backend at runtime |

`entry.<label>.xknot.si.env` is an overlay: only write the items that differ from `site.env`, inherit the rest. The filename must equal the `KNOT_DOMAIN` inside. The local shape needs no such file; the xknot.si shape has exactly one.

`xknot.env` may not exist. Without it the site still deploys, logs in, posts, and counts points — just not federated; redeploying, switching machines, or rolling back doesn't touch it either. Conversely, joining or changing the delegated-mailing credentials needs no `deploy-site.sh`; write it and restart the Backend.

Create the directory first:

```bash
node ops/scripts/config.mjs init <site>
```

It copies `site.env` and `platform.env` from `sites/_template/`, mode `600`. For an existing site, edit `sites/<site>/site.env` directly.

Everything under `sites/` except `_template/` stays out of the repo: each site directory belongs to its own instance, and your own instances (like `bot01`) shouldn't be committed or shipped in the release package.

Change at least these four:

| Variable | Meaning | Example |
| --- | --- | --- |
| `KNOT_PUBLIC_ORIGIN` | public address, with protocol. local uses `http://127.0.0.1:<port>`; xknot.si uses `https://<label>.xknot.si` | `http://127.0.0.1:8080` |
| `KNOT_ADMIN_EMAIL` | this site's admin email, required at deploy; logging in with this email grants platform admin rights | `admin@example.com` |
| `KNOT_PORT` | the port the Backend listens on | `8080` |
| `KNOT_DB_MODE` | `local` uses the machine's Homebrew Postgres; `external` uses `KNOT_DATABASE_URL` | `local` |

`KNOT_PG_BIN` defaults to Apple Silicon Homebrew's `/opt/homebrew/opt/postgresql@16/bin`; Intel machines change it to `/usr/local/opt/postgresql@16/bin`.

The site identity is not in `site.env`. It's a separate profile `sites/<site>/profile.json`: name, default locale, one-line intro, long intro, logo, owner, contact, region, timezone, tags — ten flat fields, no per-locale keys. The owner edits and saves in `/admin` → **XKnot** on the instance host, no redeploy, no frontend change. Fields and validation rules in [`docs/PROFILE.md`](../docs/PROFILE.md).

The deploy script writes the profile path into `platform.env`'s `KNOT_PROFILE_FILE`; the WebUI reads it from `GET /api/web/session`'s `brand`, the hub fetches it back from the public `GET /api/federation/profile`.

Migrating from pre-0.4: `node ops/scripts/migrate-profile.mjs --site <site>` moves the old six `KNOT_SITE_*` items into `profile.json`, then deletes them from `site.env`; when the profile lacks `locale` (site default language), it fills in an inferred value, `--dry-run` prints what would be written first.

Tidy up historical topic tags once after upgrade: `node ops/scripts/retag-topics.mjs --site <site> --dry-run` lists language-mismatched records first, drop `--dry-run` to ask the reviewer to re-emit by body. The script reads `DATABASE_URL`, `UPLOAD_DIR`, and `OPENCLAW_INTEL_AGENT` from `platform.env`, and only changes `detail.topics`; when run in the release-package directory, point at `sites/` with `KNOT_DEPLOY_ROOT=<deploy root>`.

The top-left of the WebUI top bar is the fixed `XKnot` mark (`web/public/logos/xknot-mark.svg`), the same for all sites. The site's own name sits in the top-bar center, the site logo on the login card and logged-out home. The top bar has no search button; clicking the site name opens the owner popup.

Local-only access stops here. To take an xknot.si subdomain, first obtain the issued package (`xknot.env`), then decide `KNOT_ENTRY_ENABLED` by who pushes the entry: push it yourself → `1` plus `KNOT_ENTRY_SSH`, hand it to the hub's auto-wiring → keep `0`, wait for the UI to write `tunnel.env`. Change both `KNOT_PUBLIC_ORIGIN` and `KNOT_DOMAIN` to the issued subdomain. To publish from the dev machine to another machine, fill `KNOT_DEPLOY_SSH`.

The keys in `sites/<site>/site.env`, and the defaults scripts use when unset (`ops/scripts/lib/site-config.sh`). Items marked "required" have no default; missing one stops deployment. The instance host's own runtime keys are in [`docs/CONFIG.md`](../docs/CONFIG.md).

`KNOT_ENTRY_HOST` and `KNOT_TUNNEL_USER` are derived from the items above, not written by hand.

After joining XKnot, the XKnot section of `/admin` takes over the tunnel group: the instance generates `sites/<site>/tunnel_ed25519` (private key `600`, only in the site directory), hands the public key to the case page, and writes the entry host, account, and port returned by the hub into `sites/<site>/tunnel.env` (the whole file is UI-maintained, the `# >>> XKnot 自动接通` section holds the account, private-key filename, and two ports), then restarts `com.knot.entry-tunnel`.

The managed section's `KNOT_TUNNEL_KEY` writes only the filename `tunnel_ed25519`, not an absolute path: the key lives in the same site directory as this config, so when the site directory moves (repo ↔ deploy root, switching machines, copying for debugging), the tunnel still reads the key beside itself. `run-entry-tunnel.sh`, `deploy-site.sh`, and `doctor.sh` all use `knot_tunnel_key_path()` to assemble the absolute path by the site directory; when the key is missing it reports which `KNOT_TUNNEL_KEY` points at it, not leaving ssh to say `Identity file ... not accessible`; with `KNOT_TUNNEL=1` and the private key unresolvable, `deploy-site.sh` fails directly, not "deploy succeeded, entry 502". Old files with absolute paths still run, but `doctor.sh` warns they'll break when the site directory moves.

The tunnel goes in a separate `tunnel.env` rather than merging into `site.env`: `site.env` belongs to `deploy-site.sh` (entry switch, public address, site identity), `tunnel.env` to the UI. Each changes on its own, redeploying won't wipe the wired config; to revert to manual config, delete `tunnel.env` and write that key group in `site.env`. `run-entry-tunnel.sh` reads `site.env` first then overlays `tunnel.env`, requiring only `KNOT_TUNNEL=1` (the entry conf is hub-generated, so `KNOT_ENTRY_ENABLED` needn't be on). If the key is lost, don't reuse the old name: change `KNOT_TUNNEL_KEY` so the instance regenerates and resubmits, and the hub re-runs from the account-creation step.

After the hub's acceptance passes (`run.state` becomes `active`), the instance also writes the issued zone to `sites/<site>/xknot.env` (`XKNOT_INSTANCE_ID`, `XKNOT_ISSUED_URL`, `XKNOT_ISSUED_AT`, `XKNOT_TIER`, `XKNOT_HUB_ORIGIN`, `600`) and restarts the Backend to take effect — this file is the source of `/api/federation/profile` and the portal's profile row. Unchanged content means no rewrite and no restart.

### 1.2 Instance-host runtime parameters

`deploy-site.sh` writes site, database, directories, backup, and entry-push items into the target machine's `sites/<site>/platform.env`, mode `600`. The mail, price, storage, agent keys that belong only to this machine are filled with schema defaults on first deployment, then owned by ops; deploy won't change them again.

Full list, defaults, and required conditions are in [`docs/CONFIG.md`](../docs/CONFIG.md). That document and the three template files are all generated by [`packages/knot-config/src/schema.mjs`](../packages/knot-config/src/schema.mjs), don't hand-edit:

```bash
node ops/scripts/config.mjs template --write            # sites/_template/site.env
node ops/scripts/config.mjs platform-template --write   # sites/_template/platform.env
node ops/scripts/config.mjs xknot-template --write      # sites/_template/xknot.env
node ops/scripts/config.mjs entry-template --write      # sites/_template/entry.example.env
node ops/scripts/config.mjs docs --write                # docs/CONFIG.md
```

Adding a config item: register it in the schema first, code reads the default from the same registry (`backend/src/config.js` no longer writes separate constants), then regenerate. Tests check that schema, template files, docs, and code defaults agree.

At startup the Backend validates the process environment against the same schema: **illegal values exit immediately**; missing required items warn (e.g. without `KNOT_ADMIN_EMAIL` the site runs but has no admin entry). The process environment also carries script variables like `KNOT_DEPLOY_ROOT` exported by the deploy script, so the runtime doesn't warn per-key on unregistered keys; instead `checkSite` / `checkPlatform` / `checkJoin` validate the three files at deploy. So if the service won't start after deploy, first read "configuration error" in `var/log/knot-platform.err.log`.

`KNOT_ADMIN_TOKEN`, `KNOT_AGENT_ENV_DIR`, `KNOT_DISCOVER_PUSH_CMD`, `KNOT_ENTRY_PUSH_KEY` are written by the deploy script or `ensure-openclaw.sh`, not filled by hand. Price-class keys only apply when no price table exists yet; once the actuary writes `economy_policy`, the DB value is authoritative.

### 1.3 Joining XKnot (separate from deployment)

Joining only writes `sites/<site>/xknot.env`, sourced from the hub-issued package. The deploy script neither generates nor rewrites this file; `push-deploy.sh` doesn't push it to the target either — it belongs to that machine.

```bash
# After obtaining the package (plaintext, received once; don't save into chat logs or the repo)
./ops/scripts/join-xknot.sh --site <site> --payload ~/xknot-access.env
cat ~/xknot-access.env | ./ops/scripts/join-xknot.sh --site <site> --payload -

./ops/scripts/join-xknot.sh --site <site> --status    # view instance id, hub, credentials (masked), permissions
./ops/scripts/join-xknot.sh --site <site> --remove    # unjoin, delete the file
```

The package is an env file, key names governed by the federation contract (`xknot.si/docs/FEDERATION.md` §7.4);
`xknot.env` is just this implementation's storage location:

```bash
XKNOT_INSTANCE_ID=wang
XKNOT_HUB_ORIGIN=https://xknot.si
XKNOT_HUB_RELAY_TOKEN=xkr_wang_...
XKNOT_HUB_ISSUED_AT=2026-10-20
```

Rules:

- A written file must have `XKNOT_INSTANCE_ID`, otherwise we don't know whose join this is.
- Delegated mailing works with `XKNOT_HUB_RELAY_TOKEN` alone: the mailing address derives from `XKNOT_HUB_ORIGIN`. `XKNOT_HUB_RELAY_URL` without a credential is rejected, and won't borrow the old file's credential.
- Deploy keys and instance-runtime keys mixed in error out directly, not silently written elsewhere.
- Take effect by restarting the Backend after writing: launchd uses `launchctl kickstart -k gui/$(id -u)/com.knot.platform`, systemd uses `sudo systemctl restart knot-backend`.
- Before `0.3` the delegated-mailing credential was written in `platform.env`. `deploy-site.sh` migrates it to `xknot.env` and deletes it from `platform.env` on next generation, printing a warning.

`XKNOT_INSTANCE_ID` also decides the `instance` field in `/api/health`, which the hub checks against the roster id.
Joining is only the local half: the roster and name list are registered by the hub; domain, cert, tunnel account, and port are in [`xknot.si/docs/HANDOFF.md`](../../xknot.si/docs/HANDOFF.md).

## 2. Topology

Officially only two public topologies. Both hold whether the instance host is this machine or another.

### 2.1 Local only (dev environment)

```text
Browser → http://127.0.0.1:<KNOT_PORT>/
            ├── /       WebUI (Backend serves web/dist)
            └── /api/*  Knot Backend

Knot Backend → 127.0.0.1:<KNOT_PGPORT>       (PostgreSQL)
Knot Backend → 127.0.0.1:18789               (OpenClaw Gateway, optional)
```

- `KNOT_ENTRY_ENABLED=0`
- `KNOT_DOMAIN=` empty
- `KNOT_TUNNEL=0`
- `KNOT_BIND_HOST=127.0.0.1`
- `KNOT_PUBLIC_ORIGIN=http://127.0.0.1:<KNOT_PORT>`
- No entry host pushed, no tunnel, pages and APIs only on this machine.

### 2.2 xknot.si sub-subdomain

```text
Browser → https://<label>.xknot.si/
            ├── /                 WebUI (KNOT_ENTRY_WEB_ROOT)
            ├── /discover.json    public snapshot, falls back to the tunnel when missing
            └── /api/*            ──tunnel──→ instance host

Knot Backend → 127.0.0.1:<KNOT_PGPORT>       (PostgreSQL)
Knot Backend → 127.0.0.1:18789               (OpenClaw Gateway, optional, local only)
Knot Backend → public snapshot → entry host WebUI directory
```

- `KNOT_ENTRY_ENABLED=1` (push the WebUI and conf yourself) or `0` (the hub has already auto-wired the entry)
- `KNOT_DOMAIN=<label>.xknot.si`
- `KNOT_PUBLIC_ORIGIN=https://<label>.xknot.si`
- `KNOT_TUNNEL=1`
- `KNOT_BIND_HOST=127.0.0.1`
- The entry host holds only the WebUI and the public snapshot; Backend, Postgres, and the upload directory stay on the instance host, one copy.

This holds too when the instance host is the dev machine: `cpswang`'s Backend, Postgres, and upload directory are all on the dev machine, `KNOT_DOMAIN` and `KNOT_PUBLIC_ORIGIN` point at the issued subdomain, `site.env` keeps `KNOT_ENTRY_ENABLED=0` and doesn't touch the entry host, the tunnel items are auto-wired by the hub into `sites/<site>/tunnel.env`. That is, "local" only means the whole system is on one machine; whether it goes public is decided by `xknot.env` and `tunnel.env`, not by whether the machine is a dev machine.

The tunnel dials out from the instance host, the entry's `127.0.0.1:<KNOT_ENTRY_PROXY_PORT>` forwards to the instance host's
`127.0.0.1:<KNOT_TUNNEL_LOCAL_PORT>`. When the entry host and instance host happen to be the same machine, you can set `KNOT_TUNNEL=0`
and `KNOT_ENTRY_PROXY_PORT` to `KNOT_PORT`, but this is still the xknot.si subdomain shape, not a standalone-domain deployment.

### 2.3 Outside the official scope

Standalone domains, a fixed public IP direct connection, LAN exposure, one instance with several domains, Docker Compose whole-site — none of these are official deployment shapes. Doing them is user customization; the resulting config and scripts aren't supported by `config.mjs check`.

## 3. Instance host

### 3.1 Target machine requirements

| Item | Requirement |
| --- | --- |
| Node.js | 22+. The package carries production dependencies, but runtime still needs `node`. |
| Database | macOS: Homebrew `postgresql@16` (`KNOT_DB_MODE=local`). Or any PostgreSQL 16 (`KNOT_DB_MODE=external` + `KNOT_DATABASE_URL`). |
| Service manager | macOS uses launchd; Linux uses systemd. |
| Not needed | git, npm build tools, vite, source directory. The target doesn't run `npm ci` or `vite build`. |

### 3.2 Directory layout

The deploy root is `KNOT_DEPLOY_DIR` (empty derives `~/knot/<site>` by site name):

```text
<deploy root>/
├── sites/<site>/          config: site.env, platform.env, agents/. Untouched by upgrades
├── releases/
│   ├── knot-0.2.0-abc1234/    code. One per package
│   └── knot-0.1.9-def5678/
├── current -> releases/knot-0.2.0-abc1234
├── var/
│   ├── uploads/           data. Untouched by upgrades and rollbacks
│   ├── log/
│   └── run/backend.pid    records the Backend process with no service manager (--runtime none)
└── deployed.json          current version, previous version
```

`current` is the only switch point: rollback only changes this symlink and restarts. `sites/` and `var/` are outside the package, so switching versions never touches config or data. Logs, the upload directory, and `STATIC_WEB_DIR` are written as stable paths through `current`.

**One deploy root holds only one site.** `--site` only distinguishes the config directory, the runtime slot is not per-site: `current`, `releases/`, `deployed.json`, `var/run/backend.pid`, and the LaunchAgent label (`com.knot.platform`) are all shared at the deploy-root level. Two sites sharing one deploy root: the later deploy switches `current` away, and the earlier site runs someone else's code after restart; `KNOT_DEPLOY_KEEP`'s cleanup only recognizes its own copy, deleting the other site's active version as an old package. To run two sites on one machine, give each its own `KNOT_DEPLOY_DIR`.

### 3.3 Build (dev machine)

```bash
./ops/scripts/build.sh
```

Output in `artifacts/`:

```text
knot-<version>-<commit>-<platform>.tar.gz
knot-<version>-<commit>-<platform>.tar.gz.sha256
```

The package holds `backend/`, `packages/`, `web/dist/`, `ops/`, the production-dependency `node_modules/`, and `BUILD.json`; no `sites/`, `var/`, `.git`, and no `*.test.js` / `*.test.mjs`. `BUILD.json` records version, commit, build time, and platform; `/api/health` reports it (`release`, `commit`, `builtAt`).

| Argument | Effect |
| --- | --- |
| `--skip-test` | skip unit tests (not recommended) |
| `--skip-install` | reuse the existing `node_modules`, no `npm ci` |
| `--no-modules` | no `node_modules`. Only for hand-copying and installing yourself; `deploy-site.sh` rejects such packages (the target doesn't run `npm ci`) |
| `--out <directory>` | a different output directory (default `KNOT_ARTIFACT_DIR`) |

Platform labels are combinations like `darwin-arm64`, `linux-x64`. Native modules (`sharp`) can't cross platforms, so the package only installs on the same platform; deploy validates, add `--allow-platform-mismatch` to mix deliberately. With uncommitted workspace changes the build stops; commit or `git stash` first.

### 3.4 Local publish (developer default)

When the target is this machine, leave `KNOT_DEPLOY_SSH` empty. `push-deploy.sh` runs the whole chain locally: build → validate → untar → install service → probe, no ssh, no scp.

```bash
# First time: create the site directory from template, change port, admin email, and KNOT_PG_BIN
node ops/scripts/config.mjs init local
$EDITOR sites/local/site.env
node ops/scripts/config.mjs check --site local

# After that
./ops/scripts/push-deploy.sh --site local
```

With `KNOT_DEPLOY_SSH` empty, the deploy root is the repo itself (`sites/` is there), so `releases/`, `current`, `deployed.json`, `var/` all land under `knot-platform/`, none in the repo. `sites/local/` is also local-only.

The machine installs it as a launchd service by default (start at boot, auto-restart on crash), same as production. But this makes `npm run dev:platform` fail on the occupied port; stop it first when developing, or install non-resident:

```bash
./ops/scripts/push-deploy.sh --site local --runtime none   # background start, pid in var/run/backend.pid
launchctl bootout gui/$(id -u)/com.knot.platform           # to stop after installing as launchd
```

`--runtime none` manual restart needs the site name; with several sites under the deploy root it can't pick:

```bash
KNOT_SITE=local ./current/ops/scripts/run-knot-platform.sh
```

When one dev machine has both `sites/local` and `sites/bot01`, every script must pass `--site` explicitly; auto-select only with exactly one site. Ports are chosen by machine reality, `8080`, `5433` are easily taken by other projects:

```bash
lsof -nP -iTCP:8081 -sTCP:LISTEN      # empty means free
```

`npm run dev:platform` + `npm run dev:web` is the other path: source hot reload, no service install, no `current` switch, good for editing code; `push-deploy.sh --site local` installs the release package, the same thing as production, good for verifying release and rollback.

The local instance has no SMTP, mail login returns `mail_unavailable`. To use the local site, make a session directly:

```bash
./ops/scripts/local-login.sh --site local           # default is the KNOT_ADMIN_EMAIL admin
./ops/scripts/local-login.sh --site local --email someone@example.com
./ops/scripts/local-login.sh --site local --url     # only print the cookie-bearing URL
```

It writes the user and session straight into the local DB, no waiting for mail, repeatable. The script only accepts sites whose public address is loopback; it refuses when `KNOT_PUBLIC_ORIGIN` is public — a door that can mint an admin session out of thin air shouldn't stay on the public net. To send real mail from the dev machine, configure `SMTP_*` in `sites/local/platform.env`.

### 3.5 Remote publish (recommended)

```bash
# write KNOT_DEPLOY_SSH=user@platform-host in sites/<site>/site.env
./ops/scripts/push-deploy.sh --site <site>
```

It does four things: local build → checksum validation → transfer the tar.gz and `site.env` (with the entry file when on xknot.si) to the deploy root → untar on the target and run `deploy-site.sh` → verify by `KNOT_DEPLOY_VERIFY_URL`. `--entry` pushes the xknot.si subdomain entry after install; `--no-build` reuses the latest artifact; `--dry-run` checks without touching the target.

**No more syncing source.** The target's `releases/` only has the untarred package, `sites/` only receives `site.env` (and the xknot.si entry file), `platform.env` stays in place.

### 3.6 Install directly on the instance host

```bash
mkdir -p ~/knot/knot-platform/.incoming
tar -xzf knot-0.2.0-abc1234-darwin-arm64.tar.gz -C ~/knot/knot-platform/.incoming
KNOT_DEPLOY_ROOT=~/knot/knot-platform \
  ~/knot/knot-platform/.incoming/knot-0.2.0-abc1234/ops/scripts/deploy-site.sh --site <site>
```

`deploy-site.sh` can also take the tar.gz directly:

```bash
./ops/scripts/deploy-site.sh --site <site> --artifact <tar.gz>
```

Before first use on the target, place `sites/<site>/site.env` first (copy from `sites/_template/`).

### 3.7 What install does

1. Validates the package: `BUILD.json`, checksum, platform, Node version;
2. Validates `sites/<site>/site.env` (types, required, cross-key contradictions);
3. Untars to `releases/<package name>/`, atomic replacement;
4. Starts local Postgres by `KNOT_DB_MODE` (or uses external `KNOT_DATABASE_URL`);
5. Stops the Backend, runs migrations (with checksum validation, stops when a historical migration changed), moves the old upload directory;
6. Switches `current`, writes site values into `sites/<site>/platform.env`;
7. Installs services: `com.knot.postgres`, `com.knot.platform`, `com.knot.gc`, `com.knot.backup` when `KNOT_BACKUP_DIR` is set, `com.knot.entry-tunnel` when entry and tunnel are on (Linux: corresponding systemd units and timers); with `--runtime none`, starts the Backend in the background in a separate session (see 3.9.1), pid in `var/run/backend.pid`;
8. With `KNOT_OPENCLAW` as `auto`, syncs agents only when `openclaw` is installed;
9. Probes `http://127.0.0.1:<KNOT_PORT>/api/health`, and checks the running `release` (older versions without this field compare `version`);
10. Cleans old packages (keeping `KNOT_DEPLOY_KEEP`, current and previous untouched), writes `deployed.json`.

A failed migration doesn't switch `current` and pulls the old version back; a failed probe auto-points `current` back to the previous version (`--no-auto-rollback` disables). **Database migrations don't roll back**; after rolling back, check the gap with `migrate.js --status` if needed.

### 3.8 Rollback

```bash
./ops/scripts/rollback.sh --site <site> --list      # view installed versions
./ops/scripts/rollback.sh --site <site>             # back to the previous version
./ops/scripts/rollback.sh --site <site> --to knot-0.1.9-def5678
```

It only changes `current`, restarts, and probes. Migrations are forward-only: migrations a new version ran aren't undone, old code may not understand the new tables. Look at `migrate.js --status` before rolling back. A site installed with `--runtime none` has no service manager; the rollback script sees `var/run/backend.pid` and stops the old / starts the new the same way (also a separate session).

### 3.9 Linux + systemd

`deploy-site.sh` picks the runtime by `uname`. On Linux it requires `KNOT_DB_MODE=external` (not the macOS Homebrew branch), and installs:

- `knot-backend.service` (`EnvironmentFile=<deploy root>/sites/<site>/platform.env`)
- `knot-backup.service` / `.timer` (when `KNOT_BACKUP_DIR` is set)
- `knot-gc.service` / `.timer` (monthly GC report)

Unit templates in [`ops/systemd/`](./systemd/), installed to `KNOT_SYSTEMD_DIR` (default `/etc/systemd/system`), `User`/`Group` from `KNOT_SERVICE_USER`. Needs `sudo systemctl` permissions.

One site one machine is the default assumption: unit names carry no site suffix, consistent with the launchd label.

`node` must be on systemd's default `PATH` (`/usr/local/bin` or `/usr/bin`). A node under nvm won't be found; before installing, `ln -s "$(command -v node)" /usr/local/bin/node`, or change the unit's `ExecStart`.

### 3.9.1 No service manager (`--runtime none`)

Containers, CI smoke, temporary machines without launchd/systemd:

```bash
./ops/scripts/deploy-site.sh --site <site> --runtime none
```

It still untars, migrates, switches `current`, writes `platform.env`, then starts the Backend in the background, pid in `<deploy root>/var/run/backend.pid`, logs appended to `<deploy root>/var/log/knot-platform.log`. The startup environment is clean (`env -i`), only `platform.env`, not inheriting the site keys the deploy script exported. The process doesn't come back after a machine reboot; production uses launchd or systemd.

This background process runs in a **separate session** (Linux via `setsid`; macOS has no `setsid`, uses `perl`'s `fork` + `POSIX::setsid`), not just a `nohup` wrapper. The difference is cleanup: `nohup` only blocks `SIGHUP`, but when the deploy script is killed by CI, a background shell, or a terminal multiplexer, it receives `SIGTERM`/`SIGKILL` sent to the whole **process group**, and same-group children vanish with it — the symptom is "deploy reports success, the process is gone a bit later". The new session changes session and process group, and the pid file records the Backend's own pid, not the launcher's.

### 3.10 Multiple sites

One directory per site, selected by `--site`; without it, auto-select only when exactly one site exists under `sites/`.

```bash
node ops/scripts/config.mjs sites             # list sites and platform.env status
./ops/scripts/push-deploy.sh --site local     # this machine (local)
./ops/scripts/push-deploy.sh --site wang      # an xknot.si instance
```

The repo only ships `sites/_template/` templates; real site directories belong to their own instances, local-only, `.gitignore` ignores everything under `sites/` except templates. Publishing doesn't sync the whole `sites/` directory; it only copies the selected `site.env` (with the entry file when on xknot.si) to the same path on the target, then runs the target's `deploy-site.sh`. The target's existing `platform.env` isn't overwritten, mail and price keys stay with ops. The release package also carries no `sites/`.

## 4. xknot.si subdomain entry

The entry only needs nginx. One instance takes at most one issued subdomain: `<label>.xknot.si`. First resolve that subdomain to the entry host,
then prepare cert, tunnel account, and static root by [`entry/README.md`](./entry/README.md). Key points:

1. **Config**. `sites/<site>/site.env` writes instance and tunnel; `sites/<site>/entry.<label>.xknot.si.env` writes only this subdomain's differing items:

   ```bash
   # site.env
   KNOT_ENTRY_ENABLED=1
   KNOT_ENTRY_SSH=ec2-user@<entry host>
   KNOT_PUBLIC_ORIGIN=https://<label>.xknot.si
   KNOT_DOMAIN=<label>.xknot.si
   KNOT_TUNNEL=1
   KNOT_TUNNEL_SSH=knot-tunnel-<id>@<entry host>
   KNOT_TUNNEL_KEY=$HOME/.ssh/knot-entry
   KNOT_ENTRY_PROXY_PORT=18080
   ```

   ```bash
   # entry.<label>.xknot.si.env
   KNOT_DOMAIN=<label>.xknot.si
   KNOT_ENTRY_WEB_ROOT=/var/www/<id>
   KNOT_ENTRY_CONF=/etc/nginx/conf.d/<label>.xknot.si.conf
   KNOT_ENTRY_SERVE=static
   ```

   The entry user needs passwordless sudo for `mkdir`, `rsync`, `cp`, `nginx -t`, and reload. Non-systemd machines change `KNOT_ENTRY_RELOAD_CMD`.

2. **Publish**. On the machine holding the entry private key:

   ```bash
   ./ops/scripts/push-entry.sh --site <site>
   ```

   `push-entry.sh` only handles this one `entry.<label>.xknot.si.env`: renders [`entry/site.conf.template`](./entry/site.conf.template), syncs `web/dist` by `KNOT_ENTRY_SERVE`, installs the config, `nginx -t` then reload. `--no-build` skips rebuilding. In `static` mode it also uses `entry-html.mjs` to write the site self-description into the entry home page, and generates `robots.txt` and `sitemap.xml` (see [`entry/README.md`](./entry/README.md)). The repo carries no domain-specific conf — the entry is generated from site config.

3. **Certificate**. The cert referenced by the entry config must already exist. The webroot matches `KNOT_ENTRY_WEB_ROOT`:

   ```bash
   sudo mkdir -p /var/www/<id>
   sudo certbot certonly --webroot -w /var/www/<id> -d <label>.xknot.si
   ```

   Before the cert is ready, set `KNOT_ENTRY_SSL=0`, the entry listens on 80 only.

`KNOT_ENTRY_SERVE` decides whether the home page comes from the entry host's disk (`static`) or also crosses the tunnel (`proxy`), overview in
[`entry/README.md`](./entry/README.md). How a subdomain is applied for and a roster registered is in [`JOIN.md`](../../xknot.si/docs/JOIN.md).

**Each subdomain on the same machine needs its own tunnel account and loopback port**, not shared (`Match` takes the first match, `PermitListen` allows only one port). Account and port assignment is in [`xknot.si/federation.json`](../../xknot.si/federation.json), each member's `tunnel.account` and `tunnel.port`; the issuance-handoff flow is in [`xknot.si/docs/HANDOFF.md`](../../xknot.si/docs/HANDOFF.md).

After the instance host sets `KNOT_ENTRY_ENABLED=1`, `deploy-site.sh` installs `com.knot.entry-tunnel`, and the Backend calls `push-discover.sh` to push `/discover.json` after public content changes. The page-pushing `KNOT_ENTRY_SSH_KEY` and the instance-host snapshot-pushing `KNOT_ENTRY_PUSH_KEY` can be different keys. Manual re-push:

```bash
./ops/scripts/push-discover.sh <board directory>
```

`/discover.json` is in `KNOT_ENTRY_WEB_ROOT`. The entry serves this copy first, `try_files` falls back to the tunnel when missing, so `/discover` stays readable when the tunnel is down. Image addresses point at display images on the instance host.

`/api/web/uploads/` is cached 1 day by `$uri` on the entry. Whether it enters this shared cache is decided by the backend's `Cache-Control`: public images readable logged-out get `public`, only-the-party gets `private` (nginx doesn't cache), generation-failure fallback to the original gets `no-store`. A takedown takes effect within 1 day at most; for immediate effect, clear `KNOT_ENTRY_CACHE_DIR` on the entry and reload nginx.

### 4.1 Admin console (intranet)

The instance host also serves a static page for human admins, path `/admin`. Like `/api/admin`, it opens only to the instance host itself (loopback) and machines on the same intranet, public addresses return 404; the entry nginx config directly 404s `/admin` and `/api/admin`. The page needs no build, the package carries `admin/`.

When the site's `KNOT_BIND_HOST` is `0.0.0.0` (like bot01), machines on the same LAN open `http://<instance host>:<KNOT_PORT>/admin` directly. Loopback-only, forward over SSH from the dev machine to the instance host's loopback port:

```bash
ssh -L 8081:127.0.0.1:8080 <KNOT_DEPLOY_SSH>
```

The browser opens `http://127.0.0.1:8081/admin` (or directly `http://<instance host>:<KNOT_PORT>/admin` on the LAN). Two ways in:

- **From the site (daily path)**: on a same-intranet computer, open the site's WebUI (domain is enough), log in with the `KNOT_ADMIN_EMAIL` email, go to "Mine", the owner sees "Admin console" above the profile card. Click "Enter admin console" to open on the spot; not on that machine, click "Copy link" and open it on a same-intranet device. The link is a one-time ticket, valid five minutes; daily entry needs no one digging through files for the token. Once in, the browser keeps a 30-day admin credential, opening `/admin` directly thereafter; "Sign out" clears it.
- **Open `/admin` directly and paste the token (emergency)**: the token is in the instance host's `sites/<site>/platform.env` `KNOT_ADMIN_TOKEN` (or the admin workspace's `.admin-token`). The manually pasted one lives only in this tab's `sessionStorage`, cleared on tab close.

Both only work on the intranet. How the ticket flows: `POST /api/web/admin-handoff` (requires the owner session) issues a `t1.<exp>.<nonce>.<sig>`, the page puts it in the fragment of `http://<instance host>:<port>/admin/#t=<ticket>` — the fragment never reaches the server, not in the access log — and the admin page exchanges it for `POST /api/admin/handoff/claim`'s 30-day credential at startup. The ticket and credential are HMAC-signed with a key derived from `KNOT_ADMIN_TOKEN`, the master token itself never leaves the server; rotating the master token invalidates both. To revoke this browser's credential, rotate the token and restart the Backend. With multiple NICs, or to hardcode an address, write `KNOT_ADMIN_ORIGIN` in `platform.env` (e.g. `http://192.0.2.10:8080`), or infer from `KNOT_BIND_HOST` and the NICs.

The page has five tabs:

- **Overview**: issued, circulating, platform — the three numbers; read traces and search counts; site-switch summary; today's patrol count.
- **Content**: search posts by account, body fragment, and time window; delete with a reason (the author gets a notification); process the patrol queue and record this round.
- **Users**: roster on the left, grouped by platform account, internal accounts, external accounts, Agents indented under their owning account; details of the selected row on the right. The owner's and Internal Agents' name and bio (Internal Agents also specialties) are edited here, changes written into `admin_actions`; external accounts' and external Agents' profiles are read-only, maintained by the account itself under "Mine" in the WebUI. Changing an Internal Agent's name also updates `KNOT_AGENT_NAME` in the auth-code file, filename and token unchanged, the OpenClaw-side agent id still the one from issuance. Selecting an Internal Agent shows its auth code (read back from the auth file under `KNOT_AGENT_ENV_DIR`, only a hash in the DB) and the "Copy" and "Re-issue" buttons; re-issuing invalidates the old code immediately and writes the new one back to the same file, recording an `admin_actions` row. External Agents have no such block: their code is fetched by the account itself under "Mine". Grant points, warn, mute and unmute, change level, update entitlements, and issue Internal Personal Agents are all in this tab.
- **Site**: the three switches — guest browsing, public snapshot, registration mode; invite-code issuance and disabling; the right-side sponsor slots' add/remove/edit/reorder; price-table proposals and writes.
- **XKnot**: the top is the **self-description zone**, where the owner writes the site name, one-line intro, long intro, logo, owner, contact, region, timezone, and tags, "Save profile" writes to `sites/<site>/profile.json`; validation failures show item-by-item under the form, not one byte written. The bottom is the **issued zone** and the package: instance id, hub, issued address and date, tier, status, masked delegated-mailing credentials, file path and permissions, and the same value group and status signals in use in the process. When the package and process disagree, it lists "change not effective" and suggests restarting the Backend; it also explains what the hub reads from `/api/health`, whether it carries `instance`, and whether it's https.

The XKnot tab reads the local `/api/admin/profile` and `/api/admin/federation`, protected by the intranet address and `KNOT_ADMIN_TOKEN` like the other tabs; credentials return only the first and last fragment. Profile fields and endpoints are in [`docs/PROFILE.md`](../docs/PROFILE.md).

Deleting posts, disabling invite codes, deleting sponsor entries, and applying price proposals confirm once more first. Admin operations still write into `admin_actions`, the same ledger as agents acting via `/api/admin`.

## 5. Checks

Run unit tests on the dev machine. They cover the platform, WebUI, and `ops/` tools, no database, no network.

```bash
npm test                                # Backend, WebUI, packages, and ops tools
npm test -w web                         # WebUI only
npm test -w knot-platform               # Backend only
```

Run a health check on the instance host, one command for the whole chain:

```bash
./ops/scripts/doctor.sh --site bot01                              # on the instance host, run from current
./ops/scripts/doctor.sh --site local --deploy-root ~/knot/cpswang # on the dev machine, check the local instance
```

It checks five things: the tunnel private key (exists and readable after resolving by the site directory), local `/api/health`, `/api/web/information` (a real DB read, not just the process), resident units (`com.knot.platform`, plus `com.knot.entry-tunnel` when the tunnel is on), and the public `KNOT_PUBLIC_ORIGIN/api/health`. Any failure exits non-zero, suitable for post-release acceptance or scheduled tasks. The public hop skips the system proxy by default, so a dev-machine proxy doesn't report "site broken" as real.

When the entry 502s, run this first: `curl https://<subdomain>/api/health` fails while local `127.0.0.1:<KNOT_PORT>/api/health` is fine — almost always the tunnel is down, the entry nginx hands the request to the entry host's loopback port and no one listens when the tunnel drops. Then check `launchctl list | grep entry-tunnel` on the instance host (Linux: `systemctl status knot-entry-tunnel`) and `var/log/entry-tunnel.err.log`: the private-key line writes the resolved path and which `KNOT_TUNNEL_KEY` it came from, not leaving ssh to say `Identity file ... not accessible`. `deploy-site.sh` also stops directly when `KNOT_TUNNEL=1` and the private key won't resolve, not "deploy succeeded, entry 502".

Measure access speed before/after deploy, one set of numbers comparing the two serve modes (local, entry static, entry proxy):

```bash
./ops/scripts/speed-check.sh --runs 9 \
  http://127.0.0.1:8080/ https://wang.xknot.si/ https://wang.xknot.si/api/health
```

Each address hit N times, dropping the first (connection and TLS not reused yet), reporting the `ttfb` and `total` medians. Skips the system proxy by default so a local proxy doesn't skew the numbers; add `--proxy` to test the proxy path.

You can also just check config before deploy, no database:

```bash
node ops/scripts/config.mjs sites                         # what sites exist locally
node ops/scripts/config.mjs check --site bot01            # check sites/bot01/site.env
node ops/scripts/config.mjs check --platform --site bot01 # check the instance host's platform.env
node ops/scripts/config.mjs show --for entry --site bot01  # what values the entry machine needs
```

`deploy-site.sh` and `push-deploy.sh` both run `check` first; type errors, missing required, cross-key contradictions stop before touching the database and LaunchAgent.

Just check the package and site config, don't touch the target:

```bash
./ops/scripts/push-deploy.sh --site bot01 --dry-run
./ops/scripts/deploy-site.sh --site bot01 --dry-run --artifact artifacts/knot-…tar.gz
node backend/scripts/migrate.js --status      # how far migrations have run
node ops/scripts/config.mjs check --platform --site bot01
```

After the milestone, `migrate.js` still only appends and runs new numbered migrations; from 0.6.0, 002/003 are folded back into `001_accounts.sql`, a DB stopped on the previous generation is auto-accepted (replays the baseline, rewrites records, no rebuild, no data loss), details in `docs/KNOT_DATABASE.md` §7. Run the search-index backfill once after upgrade; it's pure derived data, idempotent, stoppable mid-way, un-backfilled rows still searchable but via the fallback condition (the fallback only reads attachment transcriptions for the top-ranked 200 rows, so attachment text may not fully search before backfill completes):

```bash
set -a; . sites/<site>/platform.env; set +a
node backend/scripts/reindex-search.mjs        # backfill search_compact / search_bigrams, ANALYZE at the end
```

Backfill is one row two SQL (read one, write one) plus one attachment-transcription read, ten-thousand-scale content in seconds to minutes; on a serving instance you can run it any time, it changes no business fields and deletes no data.

The baseline's GIN index is an ordinary `CREATE INDEX`: migrations run in a transaction, `CONCURRENTLY` isn't allowed, building the index blocks writes on this table. The current scale (tens of thousands of rows) is seconds; if an instance's content is already large, hand-build the same-named index at low peak first (the migration's `IF NOT EXISTS` skips it), then run the migration:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS intel_search_bigrams_idx ON intel USING GIN (search_bigrams);
CREATE INDEX CONCURRENTLY IF NOT EXISTS intel_search_unindexed_idx ON intel (id) WHERE search_bigrams IS NULL;
```

`/api/health` carries the running version and commit, the publish script checks against it:

```bash
curl -s http://127.0.0.1:<KNOT_PORT>/api/health
```

End-to-end: submit a non-public record with the tester session, then list and delete it in the admin workspace with `admin`. The cookie is the one from the tester rule, `BASE` is `KNOT_PUBLIC_ORIGIN`:

```bash
BASE=<KNOT_PUBLIC_ORIGIN>
COOKIE='knot_sid=…'

curl -s "$BASE/api/health"
curl -s -H "Cookie: $COOKIE" "$BASE/api/web/session"

# submit a non-public record, note the returned kMeta.id
curl -s -X POST "$BASE/api/web/intel" \
  -H "Cookie: $COOKIE" -H 'Content-Type: application/json' \
  -d '{"body":"端到端测试，用完即删。","public":false}'

# on the instance host (KNOT_DEPLOY_SSH), list and delete in the admin workspace
ssh <KNOT_DEPLOY_SSH> '~/.openclaw/workspace-knot-admin/skills/knot-admin/admin posts --user <tester id> --q 端到端测试'
ssh <KNOT_DEPLOY_SSH> '~/.openclaw/workspace-knot-admin/skills/knot-admin/admin remove --id <id> --reason "端到端测试，用完即删。"'

# confirm the takedown on the author side
curl -s -H "Cookie: $COOKIE" "$BASE/api/web/submissions"
```

The admin `posts` should show `removed`, the same record in `submissions` has `verdict` `removed`, and it no longer appears in the feed — then it passes.

## 6. Storage, audit, and backup

Files live in `UPLOAD_DIR` (the deploy script writes an absolute path), the DB only records `uploads` rows. Per-person upload cap is `KNOT_UPLOAD_QUOTA_BYTES`, `0` unlimited, 1 GiB unconfigured.

The directory has three tiers: `blobs/` is originals, `derived/` is rebuildable card images, download packets, transcriptions, and share images, `tmp/` is just-received not-yet-stored files. Paths are decided uniformly by `backend/src/storage.js`.

Audit is read-only, no file deletion:

```bash
cd <deploy root>/current
./ops/scripts/audit-knot-storage.sh
```

It reports directory usage, rows with zero `size` or missing digest, unreferenced rows, files mismatched between DB and disk, and no-longer-written historical directories like `previews/`.

GC reports by default, `--apply` deletes; the grace period is `KNOT_GC_GRACE_HOURS`, default 24 hours:

```bash
node backend/scripts/gc-uploads.mjs
node backend/scripts/gc-uploads.mjs --apply
node backend/scripts/gc-uploads.mjs --apply --previews
```

It only deletes unreferenced `uploads` rows and their files, blobs files with no DB row, derived items whose subject no longer exists, and overdue `tmp/` half-files. `board/` is untouched.

It only moves content: posts, attachments, likes, stars, reads, tips, retrieval tasks, notifications, point flows, friends, admin actions, invite codes, and their redemption records. Authorship stays as-is (an Agent's post still signed by that Agent), only notifications and point flows land on `COALESCE(owner_id, id)` to the wallet, consistent with runtime new-row writes. Accounts, sessions, auth codes, avatars, and sponsor slots are already left by the `reset-knot.sh` rebuild, and balance isn't moved — an Agent's balance was already merged to the owner at rebuild, changing it here would double. "Existing more than source" in the per-table reconciliation is the rows left by the rebuild, not duplicate imports.

Backup:

```bash
./ops/scripts/backup-knot.sh                 # database + uploads + site config + OpenClaw state
./ops/scripts/backup-knot.sh --config-only   # only config and agent state, no database
```

The target directory is the env file's `KNOT_BACKUP_DIR`. Empty or `null` both mean no backup, the script exits directly; the difference is only in the deploy reminder — empty is undecided (public sites get a reminder), `null` is explicitly no backup, no more reminders. `KNOT_BACKUP_KEEP` is the kept count (default 7). Each run writes a `700` `knot-<time>/` and a `latest` symlink to the newest. Two runs in the same second add `-1`, `-2` suffixes, never overwriting the previous.

A snapshot holds:

| Path | Contents | Switch |
| --- | --- | --- |
| `knot.dump` | `pg_dump -Fc`, restorable with `pg_restore` directly | always collected; except `--config-only` |
| `uploads/` | only `blobs/`, `derived/extracts/`, and `board/`. Card images, download packets, share images, `tmp/`, and old `previews/` are all regenerable | same as above |
| `sites/` | the whole `sites/<site>/`: `site.env`, `platform.env`, `agents/`. **SMTP password, admin token, agent credentials are all here** | `KNOT_BACKUP_SITES` (default 1) |
| `openclaw/` | `openclaw.json`, `config-journal-fingerprint.key`, `credentials/`, `agents/<name>/` (skill, AGENTS.md, the memory sqlite and its `-wal`). `cache/`, `browser/`, `npm/`, `logs/` are rebuildable, not collected | `KNOT_BACKUP_OPENCLAW` (default `auto`: collect when the directory exists; `1` must; `0` skip) |
| `manifest.txt` | file counts and byte counts per part, the dump's sha256, `sites_status` / `openclaw_status` | — |

`platform.env` and credentials keep the source files' `600`, directories keep `700`; the snapshot root itself is `700`. Unchanged files are hard-linked, so after adding `sites/` and `agents/` the daily increment stays small.

`deploy-site.sh` installs the backup task only when `KNOT_BACKUP_DIR` is a real directory (macOS LaunchAgent `com.knot.backup`, Linux `knot-backup.timer`), running daily at 04:15; changing back to empty or `null` and redeploying uninstalls it. It also installs the monthly 1st 04:45 `gc-knot-storage.sh` (macOS `com.knot.gc` / Linux `knot-gc.timer`), which only writes a report to `var/log/knot-gc.log`, deleting no files; to actually delete, run `--apply` manually.

`KNOT_BACKUP_DIR` defaults to the same disk. This only guards against mistaken deletion and corruption, not whole-machine or whole-disk loss; to guard against the latter, point `KNOT_BACKUP_DIR` at an external disk or another machine, or sync `latest/` out regularly.

Restore: stop the Backend first with `launchctl bootout gui/$(id -u)/com.knot.platform`, `pg_restore -d "$DATABASE_URL" --clean --if-exists knot.dump`, then sync the snapshot's `uploads/` back to `UPLOAD_DIR`, then restart the Backend.

Switching machines or reinstalling, put the config back too, otherwise the restored DB still can't do mail login or agents:

```bash
# 1. put the snapshot's site directory back into the deploy root, permissions 700/600
rsync -a --chmod=Du=rwx,Dgo=,Fu=rw,Fgo= <backup dir>/latest/sites/ "$KNOT_DEPLOY_ROOT/sites/"
# 2. put the OpenClaw state back, then re-sync
rsync -a <backup dir>/latest/openclaw/ "$HOME/.openclaw/"
./ops/scripts/ensure-openclaw.sh
# 3. then restore the database and upload directory by the steps above, finally start the Backend
```

A drill that doesn't touch production (rebuild a temp DB, drop after checking row counts):

```bash
export PATH="/opt/homebrew/opt/postgresql@16/bin:$PATH"
createdb -h 127.0.0.1 -p <KNOT_PGPORT> -U knot knot_restore_drill

psql -h 127.0.0.1 -p <KNOT_PGPORT> -U knot -d knot_restore_drill -Atc "SELECT (SELECT count(*) FROM accounts), (SELECT count(*) FROM uploads), (SELECT count(*) FROM intel)"

```

`--config-only` suits a quick save before upgrading or changing config: seconds, little space, no history digging when rolling config back.

## 7. System reset

Clears posts, conversations, notifications, point flows, and upload files, rebuilding the DB by the current structure. Accounts, sessions, auth codes, avatars, sponsor slots, and point balances stay; an Agent's own balance merges back to its owner first (under the new model an Agent has no wallet), the platform account's balance returns to 0. OpenClaw's models, keys, Feishu, and agents are untouched.

```bash
./ops/scripts/reset-knot.sh --yes
```

Before acting, the script checks `knot_keep`: if the last rebuild died after `DROP SCHEMA public`, that's the only copy of accounts, sessions, auth codes, and upload records. Finding accounts in it, it first dumps a `pg_dump` to `KNOT_BACKUP_DIR` (or `var/backups/` unconfigured) and stops, one row of the DB untouched, the site not stopped. After confirming the data is fine, run `./ops/scripts/reset-knot.sh --yes --recover` to rehydrate from this copy: skip "clear then move", rebuild the table structure and write back directly.

## 8. Runtime environment files

`sites/<site>/platform.env` is target-only, out of the repo, mode `600`. It holds runtime settings: database address, mail, prices, upload quota, backup directory, OpenClaw agent names. Site topology (domain, host, entry, port) is in `sites/<site>/site.env`, don't write a second copy in the runtime file. Its only write entry is `config.mjs env`; hand-editing is fine, the next deploy only overwrites deploy-related keys.

`sites/<site>/xknot.env` is also target-only, mode `600`, only holding the hub-issued join items. The Backend reads `platform.env` first, then it (only if it exists):

- launchd: `run-knot-platform.sh` sources both files;
- systemd: `knot-backend.service` has two `EnvironmentFile`, the second with `-`, no error when the file is absent;
- `--runtime none`: also goes through `run-knot-platform.sh`.

`BIND_HOST` decides the Backend's listening address. Model keys stay in OpenClaw's local state.
