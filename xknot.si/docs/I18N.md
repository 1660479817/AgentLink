# XKnot Federation · Internationalization and Region

Applies to the hub portal, the instance manifest, and outward documents.

Terms in [NAMING.md](NAMING.md); field contract in [FEDERATION.md](FEDERATION.md) section 4.

## 1. Language

### 1.1 Locales

The hub and `knot-platform/web` share the same set of locale tags:

| Tag | Name (native spelling) | Chinese name | Role |
|------|------------------|--------|------|
| `en` | English | 英文 | default locale, required |
| `zh-CN` | 简体中文 | 简体中文 | simplified |
| `zh-TW` | 繁體中文 | 繁体中文 | traditional |

Language tags use BCP 47. Write `en`, not `en-US`; write `zh-CN` or `zh-TW`, not `zh`.

When adding a locale, only add the locale file and manifest keys; the key names in code do not change.

### 1.2 Default and fallback

Every place that reads text follows the same chain:

```
requested language → that language's base language (zh-CN → zh) → en → the first non-empty locale in the manifest
```

- This chain covers only **UI text** (`web/src/locales/*.json`). A site's self-described `name`, `tagline`, `intro` are single-value strings since 2.x, with no per-locale mapping, so they do not fall back: whatever the owner writes is what the portal shows.
- A missing locale renders no empty line, no key name, and no placeholder.
- No machine-translation fallback.

### 1.3 URLs

Static hosting, using path prefixes, one page per locale:

| Path | Content |
|------|------|
| `/` | 302 to `/en/` |
| `/en/` | English |
| `/zh-CN/` | Simplified Chinese |
| `/zh-TW/` | Traditional Chinese |

- Every page carries `hreflang`, with `x-default` pointing to `/en/`.
- Language switching uses plain links, not `?lang=`, and does not rewrite history.
- Switching language returns to the same page.
- The page language is determined by the path, with no GeoIP and no reading of the visitor IP.

The instance's WebUI is a different matter: its default locale is set by the owner in `profile.json`'s `locale` (for the primary audience), and a locale the visitor previously picked takes priority; likewise it does not read the browser language or use GeoIP. See `knot-platform/docs/PROFILE.md`.

### 1.4 Page rules

- `document.documentElement.lang` follows the current locale: `en`, `zh-CN`, `zh-TW`.
- Numbers, dates, and relative times go through `Intl.DateTimeFormat`, `Intl.RelativeTimeFormat`, `Intl.NumberFormat`, passing the current locale.
- Relative time: "3 小时前" "3 小時前" "3 hours ago". Past 7 days, switch to absolute dates.
- Time renders in the instance's own `timezone`, not the browser timezone.
- Layout reserves English length: the same sentence is about 30% to 50% longer in English than in Chinese. Buttons, labels, and status dots do not use fixed widths.
- Leave a space between Chinese and Western characters: "每 15 分钟" "6 张卡片".

### 1.5 Identifiers that are not translated

Code identifiers render as-is: `id`, `url`, `statsUrl`, `cardsUrl`, `tier`, `status`, `up`/`degraded`/`down`/`unknown`, `formatVersion`.

Status values are always English lowercase in JSON; the UI shows local text. Translation happens only at the rendering layer.

Brand names are not translated: `XKnot`, `Knot`, `XKnot 联邦`, `xknot.si`. `Agent` is not rendered "智能体".

### 1.6 Showcase card language

L3 cards are partner content; the hub does not translate them. Cards carry their own language tag:

- Each card carries a `lang`, BCP 47, e.g. `zh-CN`, `en`, `ja`.
- The page adds a `lang` attribute to the card so the browser can pick the font, hyphenation, and reading voice accordingly.
- Cards do not participate in the UI locale switch: if the UI is English and a card is Japanese, it shows as-is.
- The hub only localizes the card shell: the title bar, "updated at", "open at origin site".

## 2. Region

### 2.1 One field: `region`

| Concept | Field | Meaning |
|------|------|------|
| Region | `region` | the country or region where the site sits (where the machine is) |
| Timezone | `timezone` | what clock the instance follows |

`region` is a single ISO 3166-1 alpha-2 code, uppercase; `GLOBAL` means it does not fall within a single country. The two are not derived from each other; both are written explicitly.

`region` refers to **where the machine is**, not the owner's nationality and not the target audience. Whom the site serves is described by the site's own content; the hub does not record it.

### 2.2 Region values

`region` is an ISO 3166-1 alpha-2 code, uppercase. `GLOBAL` is used alone, not mixed with other codes.

Do not use invented values like `Asia` or `APAC`.

### 2.3 Region grouping

The page browses by group. Groups are derived by the hub from `region`, not written into the manifest:

| Group | Chinese | English | Contains |
|------|------|---------|------|
| `global` | 全球 | Global | `region` is `GLOBAL` |
| `east-asia` | 东亚 | East Asia | CN, HK, MO, TW, JP, KR, MN |
| `southeast-asia` | 东南亚 | Southeast Asia | SG, MY, TH, VN, ID, PH, BN, KH, LA, MM, TL |
| `south-asia` | 南亚 | South Asia | IN, PK, BD, LK, NP, BT, MV, AF |
| `central-asia` | 中亚 | Central Asia | KZ, UZ, KG, TJ, TM |
| `middle-east` | 中东 | Middle East | AE, SA, QA, KW, BH, OM, IL, TR, IR, IQ, JO, LB, EG, YE, SY, PS |
| `europe` | 欧洲 | Europe | EU members + GB, CH, NO, IS, RS, UA, MD, BA, MK, AL, ME, AD, MC, SM, LI, VA |
| `north-america` | 北美 | North America | US, CA, MX, GL, BM |
| `latin-america` | 拉美 | Latin America | Central/South America and the Caribbean |
| `africa` | 非洲 | Africa | African countries |
| `oceania` | 大洋洲 | Oceania | AU, NZ, PG, FJ, etc. |
| `other` | 其他 | Other | codes not covered above |

Rules:

- One country belongs to exactly one group.
- Group order is fixed as the table above, not sorted by instance count.
- Validation rejects unknown country codes; `other` is only a runtime fallback.

### 2.4 Display location follows the egress IP

The self-described `region` is written on the day the site joins and does not follow the machine when it moves cities. The region the portal shows takes the egress IP the hub observes (the tunnel peer, GeoIP to country code), falling back to `region` only when nothing is observed. Rules and data sources in `HUB.md` section 4; here we only stress two points:

- Observed values only go to the country, no city and no IP.
- Clock: if the self-description wrote `timezone`, it always wins; only when missing does the country code derive one primary timezone, marked on the card. A derived clock errs coarse rather than pretending precision.

### 2.5 Region and law

`.si` is inside the EU. The region field describes the country or region where the instance currently sits:

- Privacy and data-subject requests in the instance's jurisdiction are handled by that instance; the hub does not answer on its behalf.
- The hub does not store visitor information by region, and region grouping does not constitute a visitor profile.
- The region label only describes location; it is not legal advice and does not mean the hub endorses the instance.

## 3. Profile format

UI text is keyed by language; the site's self-description is not keyed — whatever language the owner writes is what appears on the portal. A site's profile lives in two places: the hub writes the issued zone (`instances.json`), and the owner writes the self-described zone in the instance `/admin` (`sites/<site>/profile.json`). Below is the self-described zone:

```json
{
  "name": "Knot 旅行 新加坡",
  "tagline": "东南亚的慢旅行。",
  "intro": "收录旅途笔记、行程和当地指南。",
  "owner": "Jane Tan",
  "contact": "ops@example.test",
  "region": "SG",
  "timezone": "Asia/Singapore",
  "tags": ["旅行", "行程"]
}
```

The same entry in the issued zone (`instances.json`):

```json
{
  "id": "travel-sg",
  "url": "https://travel.xknot.si",
  "since": "2026-10-19",
  "tier": "free",
  "status": "active",
  "statsUrl": null,
  "cardsUrl": "https://travel.xknot.si/.well-known/knot-cards.json"
}
```

Hard rules:

| Rule | Notes |
|------|------|
| `name` required | the only required field; without a name the portal can only show the id |
| no empty strings | clearing a field omits the whole key, never writes `""` |
| `tags` free text | not translated, not synonym-merged; at most 9, each ≤16 chars |
| `region` uppercase | ISO 3166-1 alpha-2, or `GLOBAL` |
| `timezone` IANA | `Asia/Singapore`, not `GMT+8` |
| `url` not per-language | the portal splits locales by path prefix; an instance address is single |

Validation scripts: the self-described zone uses `xknot.si/ops/profile-schema.mjs` (the same rules block it on the instance side when writing the profile), and the issued zone uses `xknot.si/ops/validate-instances.mjs`. A manifest that fails validation is not published.

## 4. Validation

Before publishing:

```bash
node xknot.si/ops/validate-instances.mjs          # issued zone
node --test xknot.si/ops/*.test.mjs               # includes self-described zone rule tests
```

Issued-zone checks:

- `id` unique, format legal
- no self-described zone fields (`name`, `intro`, etc.)
- URL is https
- `since` is an ISO date
- `status`, `tier` within the enums

Self-described zone checks (`ops/profile-schema.mjs`, run on both fetch and write). The self-described zone is v2's ten flat fields, with no per-locale text mapping: the portal shows whatever the owner fills in; the only locale field is `locale`.

| Field | Rule |
|------|------|
| `name` | required, ≤40 chars; without it the whole profile does not count |
| `locale` | only `zh-CN` / `zh-TW` / `en`, defaulting to `zh-CN`; the instance uses it to set the first-visit language, the portal does not translate from it |
| `tagline` | ≤60 chars |
| `intro` | ≤800 chars |
| `logo` | https address, ≤300 chars |
| `owner` | ≤40 chars |
| `contact` | ≤120 chars |
| `region` | two-letter country code or `GLOBAL`; unrecognized falls to "other" |
| `timezone` | recognizable by `Intl` |
| `tags` | string array, each ≤16 chars, at most 9, case-insensitively deduplicated |

Writing a key outside these ten records a problem; for fields other than `name`, a problem only drops that one field, the rest is kept.

L3 cards have another layer of validation: `lang` is a valid BCP 47, and `url` points back to that instance's own host.

Any failure exits nonzero, for both pre-commit and pre-deploy.

## 5. Acceptance

- [ ] `/en/`, `/zh-CN/`, `/zh-TW/` have identical content, differing only in language
- [ ] each page has the correct `lang`, `hreflang`, with `x-default` pointing to `/en/`
- [ ] `/` returns 302 to `/en/`
- [ ] a block missing in all three languages is not rendered; no empty lines or key names on the page
- [ ] English text does not overflow buttons and status dots
- [ ] relative time renders in the current locale; past 7 days switches to absolute dates
- [ ] time shows in the instance's `timezone`
- [ ] region filter works by group; unknown countries fall to "other"
- [ ] the page makes no GeoIP request and does not decide language by visitor IP
- [ ] `validate-instances.mjs` returns nonzero for a bad manifest

## 6. Adding a locale

When adding `ja`, `ko`, `es`, follow this order:

1. Add that locale's file under `web/src/locales/`, with keys exactly matching `en.json`.
2. Add the tag to `LOCALES` in `web/src/lib/i18n.js` and register it in `web/src/lib/catalogs.js`.
3. Create `<locale>/index.html` under `web/`, writing that locale's `lang`, `hreflang`, `canonical`, and add it to `vite.config.js`'s `input`.
4. Both projects each keep a locale whitelist; add to both: this project's `ops/profile-schema.mjs` (`LOCALES`, validating the profile's `locale`) and `knot-platform`'s `packages/knot-locale` (the same set on the instance side).
5. Each owner changes their instance's `locale` in `/admin` — the self-described zone is one flat text, not split by locale, so there is no second language to fill in.
6. Build inside `web/`, then run validation and portal tests.

RTL languages such as Arabic need separate layout adaptation, handled as an independent milestone.

Traditional follows Taiwan usage. Hong Kong usage differences will be split into a separate locale only when a clear need appears.
